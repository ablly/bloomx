## 设计决策

1. **继续使用单一 callable function。**
   `runAdminAction` 既负责创建动作请求，也负责审批/拒绝已有请求。这样前端只接一个服务端入口，权限和审计逻辑集中维护。

2. **动作请求默认进入 `pending_approval`。**
   前端敏感按钮不直接改数据，而是创建可审批请求；审计页再触发真实执行。

3. **第一批真实执行只做有限白名单。**
   可以执行冻结/解冻、提交复核、重放排队和导出摘要；涉及资金、结算、退款和支付 Provider 的动作继续停留在审批请求/审计阶段。

4. **审批执行使用事务防重入。**
   服务端读取 audit log 当前状态，已执行或已拒绝的请求不能再次执行，避免重复点击造成多次写入。

5. **审计日志是控制平面。**
   `audit_logs` 记录 requestId、原始动作、目标集合、目标文档、执行人、审批人、状态、错误和前后摘要，后台审计页以它为准。

## 风险与缓解

- **真实执行范围过大**：只允许白名单动作，未带必要参数的角色/积分动作拒绝执行。
- **重复审批**：事务里检查状态，已终态的请求直接报错。
- **前端误触**：普通页面只提交请求，真实执行集中到审计页。
- **权限绕过**：所有审批和执行都在 callable function 内重新验证管理员身份。
