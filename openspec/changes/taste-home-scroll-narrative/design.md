## Context

BloomX 是模型 API 能力交易市场，首页需要把“商家上架、用户订阅、调用、退款、结算、支付、商家申请”解释成一个交易闭环，而不是多个互相竞争的营销板块。用户在浏览评论中明确要求删除 Hero 眉标，并把下方所有内容融合进上方滑动页面。

## Goals / Non-Goals

**Goals:**

- 使用一个高保真滚动叙事承载首页主要内容。
- 每个场景左侧承载标题、摘要、要点或表单，右侧承载业务可视化。
- 粒子动效缓慢浮现，不遮挡文字，不影响移动端阅读。
- 保留 Stripe 积分套餐结账入口和商家申请提交入口。
- 删除重复的下方旧区块，降低页面长度和内容冗余。
- 给出支付、个人中心和上线商业化风险检查结论。

**Non-Goals:**

- 不新增第三方动画库或视觉资产。
- 不实现新的支付 provider、Webhook 或商家自动分账。
- 不在本轮重写 Dashboard、Marketplace 或 Admin 的核心业务逻辑。
- 不添加与 BloomX 交易闭环无关的填充内容。

## Decisions

1. **单一滚动叙事替代多区块堆叠。**
   - 原因：用户评论明确要求把原有区块内容融合进上方滚动页面；单一 sticky 容器可以让信息逐步显现，减少重复。

2. **左文右图的非对称场景系统。**
   - 原因：保留可读性，让每张“滚动页面”的左侧负责业务内容，右侧负责模型表、积分、申请、结算等状态可视化。

3. **粒子只做慢速空间层次。**
   - 原因：用户要求粒子缓慢浮现；动效应服务信息层级，避免亮色噪声和视觉遮挡。

4. **新首页直接复用现有服务调用。**
   - 原因：支付和商家申请已经有服务入口，本轮只移动交互位置，不改资金和权限边界。

## Risks / Trade-offs

- Sticky 叙事依赖滚动位置，移动端高度不足时需要压缩排版并禁用过度装饰。
- 把表单放入 Hero 叙事会增加组件复杂度，但能满足用户“这个也是”的融合要求。
- 支付、退款、个人中心的生产可用性不能只靠前端构建确认，仍需要真实环境变量、Stripe Dashboard、Firebase 权限、Webhook 和人工运营流程复核。

## Migration Plan

1. 创建新的滚动场景数据和视觉组件。
2. 删除 Hero 眉标，并让导航跳转到对应场景位置。
3. 将原有首页区块从 `LandingPage` 移除，只保留 Hero、Footer 和 AuthModal。
4. 将 Stripe Checkout 和商家申请服务调用接入新场景。
5. 运行构建、规格、工作流和项目简报检查。
