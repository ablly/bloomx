## Context

当前项目已接入 OpenSpec + Superpowers，并建立了产品、UI 设计、交付三组基线规格。昨天首页新增了视频背景、粒子标题和 3D 货币深度场，但部分新增中文字符串在源码中已经变成乱码。用户同时明确要求：后续所有流程都使用 n8n 工作流，并授权使用相关 skill 与 MCP。

## Goals / Non-Goals

**Goals:**
- 修复首页新增中文文案乱码。
- 保留现有首页动效和交易流动视觉方向，不重做视觉系统。
- 把 n8n 作为默认流程自动化平台写入项目协议、交付文档和 OpenSpec 规格。
- 新增一个用户可访问的 n8n 工作流总览页面。
- 把“完成后必须运行并自审”写入项目协议和规格。
- 把“审核无误后默认提交并推送 GitHub”写入项目协议和规格。
- 让本次改动成为第一条可验证的 OpenSpec change。

**Non-Goals:**
- 不在本次重构 n8n 工作流本身。
- 不迁移或删除历史 Make 文档。
- 不处理所有历史乱码文件，只处理本次首页相关代码和交付规则。
- 不做 Cloudflare 线上部署。

## Decisions

1. **首页文案直接修正为源码内有效中文**
   - 原因：乱码已经进入 TSX 字符串，必须直接替换，否则构建不会报错但用户会看到坏文本。
   - 替代方案：只改 i18n JSON。该方案不能覆盖当前组件内硬编码乱码。

2. **App 注释改为英文或移除乱码**
   - 原因：注释不影响运行，但会污染后续维护上下文。
   - 替代方案：全部中文注释。当前项目 PowerShell 输出存在编码显示问题，源码注释优先保持简单 ASCII 更稳。

3. **n8n 作为新流程默认平台，Make 保留为历史资料**
   - 原因：用户明确指定所有流程使用 n8n；项目已有 n8n event bus 和工作流记录。
   - 替代方案：n8n 与 Make 双轨。该方案会增加运维歧义，不再作为默认。

4. **本次只做代码和规格验证，不启动部署**
   - 原因：当前目标是修复和建立交付闭环，部署需要环境变量和线上权限检查，适合单独 change。

5. **工作流访问页采用静态 HTML**
   - 原因：工作流入口属于运营查看资料，不需要进入 React 路由，也可以直接由 Vite/Cloudflare 静态服务提供。
   - 替代方案：做成 React 页面。当前没有必要增加路由和鉴权复杂度。

6. **GitHub 推送只纳入本次范围文件**
   - 原因：当前工作区存在历史未提交改动，自动全量提交会污染提交边界。
   - 替代方案：全部提交。该方案不利于回溯和回滚。

## Risks / Trade-offs

- **风险：只修首页相关乱码，其他历史文档仍有编码显示问题** -> 后续可单独开 `normalize-project-docs-encoding` change。
- **风险：n8n 规则写入后，旧 Make 文档仍容易被误读** -> 在 AGENTS 和交付流程文档中明确 Make 为历史参考。
- **风险：首页动效仍可能存在移动端性能压力** -> 本次保留现状，通过构建和本地运行检查发现明显问题。
- **风险：n8n 编辑页需要登录** -> 访问页会同时提供 Production Webhook 和说明，编辑页权限由 n8n 账号控制。
- **风险：当前工作区有历史未提交改动** -> 本次只 stage 当前 change 相关文件，其余保持原样。

## Migration Plan

1. 创建 OpenSpec change。
2. 写入 delta specs、design、tasks。
3. 修复首页文案和交付规则文档。
4. 运行 OpenSpec change 校验、全量规格校验和生产构建。
5. 若通过，更新 tasks 并准备归档；若失败，先修复再交付。
